Problem & constraints

The task is to predict a Fantasy Premier League player’s points in the next gameweek. The central question is chronological: what information could a model actually have known when making that prediction?

My contribution

I implemented the pipeline from completed snapshots to model comparison: validation, time-aware features, expanding folds, baselines and ridge regression. I packaged the workflow with portable model artefacts, verified DuckDB storage, a command-line interface and a read-only local API.

Approach & decisions

  1. Completed snapshots
  2. As-of features at t
  3. Train on earlier targets
  4. Score target t+1
  1. Validate completed, season-tagged gameweek snapshots before feature engineering. Build recent-form and season-to-date features from information available at gameweek t, paired with the target at t+1.
  2. Compare baselines and ridge regression in forward-moving evaluation folds. Each fold trains on earlier target gameweeks and scores the following one, keeping future outcomes out of the features.
  3. Package the workflow as command-line tools with portable model artifacts, DuckDB storage and a read-only local API. Add automated checks and a non-root Docker workflow for repeatable local use.

Results & interpretation

On ten historical test gameweeks (GW6–15, 2024–25), ridge regression produced the lowest mean absolute error of the four candidates: 1.110 points, compared with 1.130 for the three-observation mean baseline. The comparison covers 6,684 player-gameweek rows. The difference is modest; using the recent-form baseline makes that clearer than comparing only against the weaker training-window mean.

Mean absolute error (MAE) measures the average size of a points error without regard to its direction. Root mean squared error (RMSE) puts more weight on larger misses. Ridge has MAE 1.110 and RMSE 2.019 in the retained evaluation. These are useful aggregate descriptions, but a small average error does not by itself show that a model identifies the best players to select.

That is why the comparison also reports ranking metrics. Spearman correlation describes ordering, while normalised discounted cumulative gain at ten (NDCG@10) concentrates attention near the top of the list. Ridge records NDCG@10 of 0.226 and top-ten overlap of 0.170. Those values belong alongside the modest error improvement when discussing player-selection usefulness.

The evaluation starts at GW6 and ends at GW15. The next adjacent-player coverage value is 0.8987 between GW15 and GW16, below the predefined 0.90 threshold. Stopping at that boundary preserves the stated data rule. It also limits the claim: this is not evidence of performance through the entire season.

Failure cases & limits

This is a partial-season historical evaluation, not a live prediction service or a test of full-season robustness. The workflow predicts individual player points; it does not optimise squads, transfers, captaincy or budgets. Fixture schedules, opponent strength, injuries, expected line-ups and price history are outside this feature set. Synthetic examples check software behaviour, not football prediction quality.

Engineering and verification

The snapshot reader rejects duplicate player IDs with DataContractError and rejects an empty gameweek as completed data. Checking these conditions before feature generation prevents ambiguous or incomplete records from entering the model workflow.

Features use information available at gameweek t and are paired with the outcome at t+1. Expanding folds train on earlier target weeks before scoring the next one. A random split would not preserve that temporal separation.

Portable JSON model artefacts and verified DuckDB batches support the model-bound local API. The operations guide explains the interface; automated tests and a non-root Docker workflow support local use.

The public repository retains aggregate figures and file-level provenance rather than source player records or a fitted model. Its deterministic synthetic example exercises the software; reproducing the historical evaluation requires the documented source inputs.

A static walkthrough

Begin with completed snapshots from one season. Validate their shape, gameweek sequence and coverage before computing player history. Construct features from past observations only, then fit a candidate on earlier target weeks and evaluate it on the following target week. Repeat as the training window grows.

Compare the saved error and ranking metrics with the recent-form baselines before drawing a conclusion. The diagram and table on this page describe that retained process; they do not accept new player data or generate a forecast in your browser. For an executable example, the repository walkthrough and data contract explain the local inputs and commands.

Next step

Evaluate a broader, separately specified window with clear coverage rules before adding model complexity. New injury or line-up features would also need an explicit record of when the information became available.
