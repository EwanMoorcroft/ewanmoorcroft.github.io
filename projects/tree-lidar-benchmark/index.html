Benchmarking six methods for 3D tree segmentation

How can different tree-segmentation methods be compared under the same scoring rules? A common evaluation workflow for existing methods on UAV LiDAR point clouds.

Problem & constraints

Individual-tree segmentation separates a forest point cloud into individual trees. A useful benchmark needs to ask two different questions: did a method recognise the right tree instances, and how closely did their point sets overlap? Treating both as a single “accuracy” number hides the distinction. My dissertation work brings six existing methods into one evaluation workflow, using FOR-instance UAV/airborne LiDAR data.

My contribution

I integrated the methods into a benchmark and implemented the shared aligned-label evaluation and result-verification workflow. The models, architectures and FOR-instance dataset are the work of their original authors. This distinction matters: the portfolio demonstrates comparison, integration and evaluation engineering, rather than a claim to have invented six segmentation methods.

The practical challenge is maintaining a clear contract between outputs and evidence. A route name, configuration and retained result need to refer to the same thing throughout the comparison. The public verification layer checks identities and coverage as well as arithmetic, so a plausible-looking table is not enough on its own.

Approach & decisions

  1. Point-aligned labels
  2. Eligibility checks
  3. One-to-one matches
  4. Pooled instance metrics
  1. Align outputs before scoring. A predicted label has meaning only when it refers to the same source point as the reference label. I work with point-aligned labels so differences in point order cannot masquerade as differences in segmentation quality. This interface lets the evaluator compare heterogeneous methods without claiming that their original input processing is identical.
  2. Fix eligibility and matching rules. Reference trees use positive instance IDs in semantic classes 4, 5 or 6. A prediction is excluded only when more than half of its aligned points are class 3; exactly 50% remains eligible. An intersection-over-union threshold of 0.50 determines candidate matches. Deterministic one-to-one matching maximises the number of valid pairs, preventing one prediction from receiving credit for several trees.
  3. Keep result routes separate. The author-released route and project-adapted route represent different configurations, not equally funded experimental treatments. TreeX and TLS2trees use parameter selection rather than neural fine-tuning. Preserving those distinctions makes the comparison more informative than a single table labelled “before and after training”.

Results & interpretation

The published benchmark covers 11 held-out plots, 323 reference trees and 49,709,922 points. ForestFormer3D has the highest pooled instance-recognition F1 on the project-adapted route in this comparison: 0.844. This is an instance score, not 84.4% point accuracy. The table shows all six methods so the leading result does not hide the spread or the route-specific changes.

Pooled precision and recall are reconstructed after true positives, false positives and false negatives have been summed across plots. Their harmonic mean gives micro F1. It answers how well tree instances were recognised under this protocol; it does not say how accurately every canopy point was classified. Pointwise overlap describes a different aspect of the match.

ForestFormer3D, ForAINet and SegmentAnyTree change relatively modestly between routes. TreeLearn and TLS2trees change more, while TreeX is slightly lower on its project-adapted route. Those are descriptions of retained configurations. Different amounts of development work mean that the size of a change cannot be interpreted as a controlled comparison of adaptation methods.

Intersection over union divides the points shared by a reference and prediction by the points belonging to either. One-to-one matching then makes missed and extra trees count explicitly. A split tree can leave extra predictions; a merged prediction can leave reference trees unmatched. These are consequences of the scoring rules, not invented counts of particular failures in this benchmark.

Failure cases & limits

Engineering and verification

The public evaluator rejects changes to reference classes, ignored ID, boundary rule or overlap threshold under the same protocol name. This prevents a different scoring definition from silently inheriting an established label. Literal identifiers remain unchanged: the human-facing author-released and project-adapted labels map to published_default and development_tuned respectively.

The public package exposes verify and summary commands. Its manifest, route inventory and per-plot tables support deterministic aggregate reconstruction without distributing the larger point clouds. The source includes tests for the evaluator and verification interface. These links are an inspection path; the scientific runs were not repeated as part of building this website.

For a technical review, start with the evaluator, then the verification module, result manifest and provenance note. That order separates the implemented scoring contract, retained evidence and unavailable original inputs. Reproducing the full experiment requires more than running the aggregate verifier.

What I take from this

The useful engineering lesson is that comparability is something to establish, not something to assume from a common metric name. Output alignment, eligibility rules and route identity all affect what a result means. Making those choices inspectable is part of the contribution.

A justified next step would be a systematically selected failure analysis across plots, with a stated selection rule and permission to publish each example. That would add information about where methods split, merge or miss trees. It is future work here; a deliberately clean illustration cannot stand in for it.
